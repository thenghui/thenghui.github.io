备注: 关键概念:AI 是 stateless 的 — 没有持久记忆。 每一个 session、每一次 task invocation 都是一次 fresh context load。 AI 对你项目的理解 = 100% 取决于你 feed 的 context。 这也是为什么 "写很长的 prompt" 不可持续 — 真正的 context 应该住在 Project Brain 里,prompt 保持 minimal。

备注: Context engineering 的核心动作 = 把工程师脑中的 mental model 翻译成 AI 能精确 parse 的结构化文档。 不是把所有东西丢给 AI,而是有结构、有层次地组织。 接下来讲这个结构分三层。

备注: Context 分三层 — 这是整个 Project Brain 的骨架: 1. Static Constraints (_DOCS/): 定义架构、business rules、API contracts。教 AI "什么 baseline rule 永远不能违背",防止 AI 乱 refactor。 2. Dynamic State (CurrentStatus.md): progress tracking + decision history。教 AI "我们在哪、为什么这么选",让 cross-session 无缝衔接。 3. Ephemeral Session (chat window): 实时 task workspace。容易累积 noise — task 完成后必须 New Session 清掉,但 output 要先写回 state layer。 三层各司其职,Part 2 会讲怎么维护。

备注: 这是 Part 1 的 hero diagram。 左侧: Prompt (minimal) → 触发 AI Coding Agent。 右侧: Project Brain = 两个 subgraph: - _DOCS (mint/绿色 pill): PRD, Architecture, Design, Database, API — static constraints & specs。 - _TASK (lavender/purple pill): CurrentStatus.md + Handover log — dynamic state & rationale。 Brain → 按 on-demand 注入 context 给 Agent。 强调: Prompt 保持 minimal,真正 context 住 Brain。 Design.md 要记录 core dependencies 的精确版本,防止 AI 调到 deprecated API。

备注: 很多人问:"我已经有 README 了,不够吗?" README 是给 humans 看的 — install + run。 Brain 是给 AI agents 看的 — structured knowledge repo。 README 是 Brain 的一个子集,但远远不够。

备注: _DOCS vs _TASK 的分工: - _DOCS = "事实/参数/结构" — 客观的项目标准。一旦写好相对稳定。Design.md 特别记 dependency versions。 - _TASK = "进行中的记录、计划" — 会变。CurrentStatus.md 记 progress + evaluated options + 为什么选这个。 这个 dual-track 是 Part 2 workflow 的基础。

备注: 每个 stage 的人机分工。核心信息:Human 是 driver,AI 是 copilot/executor。 - PRD: 人定商业目标 + boundaries,AI 帮 refine edge cases + 格式化。 - PoC: 人定 UI/UX 方向,AI 在 Google AI Studio 快速搭 prototype。 - Architecture: 人选 tech stack + dependency versions,AI 生成 _DOCS 文档。 - Coding: 人派 task + 监督,AI 读 Brain 规则生成 production code。 - Validation: 人跑测试 + review,AI 根据 error log 自我修正。 - CurrentStatus: 人 review progress + approve rationale,AI 自动 log。 重点: 人永远在 driver seat,不要变成 passenger。

备注: 我的开发 mantra (中文版:"先做模作样,之后像模像样,最后有模有样"): 1. Mock it — 用 Google AI Studio 快速搭 PoC scaffold,先有个能看的东西。 2. Make it — 建立 _DOCS 把架构约束 freeze 住,让 AI 不能乱 redesign。 3. Master it — Coding Agent 根据 Brain 产出 production-grade 系统。 这个三步是 Part 2 的核心节奏。等下有 live demo 演示第一步。

备注: CurrentStatus.md 的 4 element structure — cross-session 连续性的关键: 1. Completed — 做完了什么,带 file reference。 2. In Progress — 正在做什么。 3. Options Considered — 评估过哪些选项。 4. Decision & Rationale — 选了哪个 + 为什么。最重要的 field。 为什么 Rationale 重要?因为 3 个月后你自己都会忘记为什么当初选 B 不选 A,AI 更不可能猜到。 下一个 slide 看真实例子。

备注: 真实例子 — PDF 背景调查报告导出功能。 Completed: Supabase Auth + DB schema 已做完。 In Progress: PDF 导出。 Options: A (client-side jspdf) vs B (server-side Puppeteer)。 Decision: B。Rationale: 报告含 PII + 复杂多页 CSS print layout,server-side 保证跨设备视觉一致 + 合规。 注意 Rationale 写得很具体 — 不是 "B 比较好",而是为什么 B 在这个场景下对。 新 session 打开时,把这段贴进去,AI 立刻知道现状 + 为什么选 B,不会重新提议 A。

备注: 为什么不能一个 chat window 跑完整个项目 — 两个原因: 1. Token O(N²): LLM interaction 每次都要 send 所有历史 turns。50-turn session,每个新 request 带 tens of thousands 历史 tokens,total token consumption 是 quadratic 增长 → API cost 爆炸 + latency 上升。 2. Context contamination: 长 session 累积 obsolete debug logs + 失败 trial code + stale discussion。LLM 有 "Lost in the Middle" 现象 — context 越长,中间的信息越容易被忽略;还有 Instruction Drift — 模型忘记最初的设计约束,hallucination 率上升。 这是 empirical 现象,不是玄学。

备注: 一句话总结: Brain 是 persistent state across sessions;Session 只是 temporary workspace。 Module 做完 → 清掉 session workspace (New Session),保留 persistent Brain。 这是接下来 Golden Rule 的核心。

备注: Golden Rule 的 4 步 loop: 1. Update CurrentStatus.md — 把 progress + decision rationale 持久化到 Brain。 2. Close current session — flush 掉 O(N²) token overhead + 历史噪音。 3. Open NEW SESSION — 100% clean context,peak reasoning quality。 4. 在新 session 载入 CurrentStatus.md 开始下一个 task。 这个 loop 是 session lifecycle discipline 的核心。每一页流程图最后那个橙色 node 就是 New Session。

备注: Part 2 的收尾一句: Finish a module → flush the session → keep the Brain。 停顿,让观众记住。

备注: Brownfield 的核心原则: 不要试图一次性把整个 legacy system 文档化 — 那是灾难。 而是 on-demand — 你碰哪个 module,就把那个 module 相关的 Brain 写起来。 3 个月后你自然就有一套实用的 production-grade Brain。 这是增量构建,不是 big-bang 文档工程。

备注: 5 步增量路径 — 不是一次性做,是 on-demand: Step 1 Architecture.md — outline module boundaries, tech stack, global constraints。 Step 2 Design.md — 如果碰 UI,记 component libraries + design system。 Step 3 Database.md — 碰 data entities 时,让 AI summarize schema specs。 Step 4 API.md — refactor API endpoints 时,update request/response contracts。 Step 5 CurrentStatus.md — 每个任务都记 progress + rationale。 关键: 这些都是 "碰到了才写",不是 upfront big-bang。

备注: 强调: Project Brain 不是某个 tech stack 专属。 不管你用 Java/Spring, C#/.NET, Python, Node, Go — 这套结构 universal。 - 改 data entities → AI summarize 进 Database.md - refactor API → 更新 API.md Brain 是 methodology,不是工具。3 个月后你自然有一套 production-grade Brain。

备注: Part 4 开始。30 分钟。 Debug 范式转换: 从 blind StackOverflow trial-and-error → Context Collection + AI Hypothesis Generation。

备注: 两个 debug flow 对比: Legacy (上方 muted): Error → Google → StackOverflow → blind copy-paste → hours wasted。Blind & time-consuming。 Modern (下方): Error → Reproduce → Collect complete context → AI generate hypotheses → Engineer verify → Apply targeted fix → Document。Systematic & efficient。 AI 的核心 strength = 快速提出 2-3 个 testable root-cause hypotheses,而不是直接给答案。 Engineer 的工作 = verify 哪个 hypothesis 对 (breakpoint / log / unit test),不是盲试。

备注: 7 步 AI debugging loop: 1. Reproduce — 确保错误能稳定复现,观察一致行为。 2. Collect Context — 绝对不要只跟 AI 说 "it broke"。完整 context: logs + code + line nos + env。 3. Ask AI — 把完整 context 给 AI 评估 potential root causes。 4. Generate Hypotheses — AI 的核心 strength = 快速提出 2-3 个 testable root-cause hypotheses。 5. Verify — 工程师验证哪个 hypothesis 对 (breakpoint / log / unit test)。 6. Fix — 让 AI 针对验证过的 root cause 写 targeted fix。 7. Document — 如果这个问题 reveal 了一个 common pitfall,记进 Conventions.md 或 debug notes,update Brain。 重点: AI 给 hypotheses,人 verify,不是 AI 直接给答案人盲信。

备注: 强调 anti-pattern: 不要只跟 AI 说 "it broke" / "报错了"。 Garbage context in = garbage hypotheses out。 AI 没有 telepathy — 它只能基于你给的 context 推理。 下一页给 checklist。

备注: 5 element context checklist — 提交 bug 给 AI 时永远包含: 1. 完整 error logs + uncut stack traces — 绝对不要截断 log!被截掉的那行可能就是 root cause。 2. 相关 source files + 精确 line numbers。 3. Expected behavior (你期望发生什么)。 4. Actual behavior (实际发生什么)。 5. Environment & state information (runtime, OS, dependency versions, 当前 state)。 这 5 个都给齐,AI 的 hypotheses 质量会质变。

备注: 7-step loop 的最后一步常被忽略: Document。 如果这个 bug reveal 了一个 common pitfall (比如某个 API 在特定环境下会 silent fail),记进 Conventions.md 或 debug notes。 下次 AI 遇到类似情况,Brain 里有记录,就不会重复踩。 "A bug fixed once is progress. A bug prevented forever is engineering."

备注: Q&A prompt 2。让观众思考: 明天就开始建 Brain,你会先写哪个 doc? 常见回答: Architecture.md (定边界) 或 Database.md (定 schema) 或 API.md (定 contract)。 没有标准答案 — 取决于他们项目当前最痛的 context gap 是什么。 把这个讨论连回 Part 3 的 on-demand 原则: 先写你最常碰的那个。 2-3 分钟讨论。

备注: 核心收尾思想: 工具会变,原则不变。 Prompt Engineering → Context Engineering → Loop Engineering,名词在演进,但 "为 stateless agent 管理 context" 这个 discipline 不变。 今天的 Brain 结构是当下的最佳实践,但背后的 invariant (Input→Process→Output, 管理 context) 是永恒的。
